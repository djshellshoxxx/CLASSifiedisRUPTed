## Interrupted-restore reasoning

The new test wraps the memory storage adapter's transaction method and forwards
the underlying transaction options and lifetime-bound store methods.

In `packages/vault/src/vault.ts`, restoration first stages the identity with
`tx.records.put`, then restores each admitted record with
`tx.records.restore`. The test intercepts only `restore`; it forwards the
first call to the real underlying store and throws before forwarding the
second call. Reaching that second call implies the first restore succeeded,
because the production loop immediately returns a failed restore result.

The underlying `createStorage.runTx` rolls back when its callback throws.
After the injected exception, the test checks that the vault is uninitialized
and neither record is present. It disables the injected exception and retries
on the **same destination vault**, rather than creating a replacement.
The vault's exclusive-operation flag is cleared in `finally`, and the failed
restoration path locks the temporary identity. The retry checks the principal,
deterministic signature, archived data and normalized location preferences.

The `Storage` annotation contextually types the wrapper's generic transaction
method. Root subsequently reported that the complete repository typecheck at
this exact PR source passed with exit 0. This reviewer did not run that
compiler invocation or independently reproduce its result.

## Coverage and qualification limits

The mixed fixture supplies the complete production registry but populates only
archive, publication and location records. It therefore does not establish
joint recovery of every registered record type. Normal domain-reader
acceptance and a mixed fixture containing retained, notification, barter,
listing and revision records remain separate coverage.

The encrypted-storage tests use `fake-indexeddb` with the production vault and
cryptography implementation. They do not replace native-browser persistence
qualification. The interruption test uses the memory adapter; it does not
simulate an IndexedDB commit failure or power loss.

The backward-compatibility fixture is generated by current v1 code with a
smaller codec registry. It establishes that supported subset compatibility,
not acceptance of an archival corpus of historical backup files.

No application tests were executed by this reviewer. Root's focused test run
was still in progress when this document was written. Current-head domain,
browser and CLI results must be recorded separately; no old, queued,
cancelled or incomplete run is counted as a pass.

## Nonblocking follow-on improvement

Use distinct archive-record and archived-listing IDs in a future mixed fixture.
The production archive model treats those as separate identities; the current
shared fixture value does not break this test, but distinct values would better
protect that distinction.
