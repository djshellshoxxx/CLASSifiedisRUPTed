## Source-confirmed invariant failure and bounded repair
The prior `blobStore` appended an encrypted blob's `{tenant, ref}` to a `shredded` array whenever `detach`/orphan cleanup removed it. If a caller deleted the **final holder** and then put the same content-addressed encrypted bytes back in the **same write transaction** and attached a new holder, `shredded()` still requested key destruction even though the blob would be present and held at commit. A key owner acting on that successful transaction's returned list could make live data undecryptable. This is a source-level correctness/integrity defect; it is **not** a demonstrated real-world incident or proof an unauthorized caller can reach this API.

The correction uses an insertion-ordered `Map` of pending shred requests keyed by collision-safe `JSON.stringify([tenant, ref])`. Encrypted removals add an intent; either successful `put` path cancels the intent for exactly that tenant and content ref. Subsequent genuine final deletion re-adds the intent. The public `shredded()` remains an array snapshot. Existing holder lifecycle, content hashing, transaction rollback, signed/encrypted v1 backup, signing identities, per-tenant keys, product limits and workflow settings are unchanged. Documentation now expressly says key destruction must occur only after successful commit, using final output rather than a partial observation during a transaction; application-level key-store atomicity remains a separate contract.

## Test-first, QA and execution boundaries

It uploads an encrypted P1 blob, attaches a holder, removes the last holder within a transaction, observes the **intermediate** shred request, re-puts identical bytes and reattaches the holder. The final pending shred list must omit that live blob and its bytes/holder must remain readable after commit; an independent later genuine final-holder deletion must still request shredding and erase the blob.
