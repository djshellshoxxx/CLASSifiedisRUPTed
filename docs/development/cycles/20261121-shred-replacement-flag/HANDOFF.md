## Source-derived behavior and bounded correction

PR #95 makes `shredded()` track pending encrypted key destruction by tenant and content ref, cancelling a pending shred on **any** subsequent successful blob `put` with the same tenant and bytes. That is correct if the final blob remains encrypted, but the same bytes can be reinserted as **unencrypted P0** after final-holder detach. The previous encrypted object's key is then obsolete despite the new *unencrypted* blob retaining the same content address. The unconditional cancellation silently discards the old key-destruction request. This is an integrity/retention contract issue in the storage API, **not** demonstrated key-store misuse or unauthorized user access.

The child now cancels the pending shred only when the **actually stored** existing or newly inserted blob row is marked `encrypted`. For a same-byte unencrypted replacement it preserves the old encrypted object's tenant/ref shred intent. The code updates the `shredded()` docstring to describe this distinction. No signature/v1 backup envelope, signing identity, cryptography, content hash, per-tenant scoping, byte limit, privacy-admission rule, product cap, workflow, timeout or dependency changed.

The new shared `storageContractSuite` acceptance runs under memory, SQLite and fake IndexedDB. It seeds an encrypted P1 blob with a holder, detaches its final holder inside one transaction, re-puts the **same bytes** as P0 unencrypted, attaches a replacement holder, and demands the old key's shred intent while the final unencrypted bytes and holder persist after commit. PR #95 source would return `pendingShreds: []` on this path; this is a **source-predicted RED**, not an executed parent-source failing Vitest run.
