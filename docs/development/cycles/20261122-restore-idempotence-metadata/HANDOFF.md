## Source-confirmed false-identical recovery path
The old `tx.records.restore(rec, idx)` returned `ok('identical')` whenever the existing row matched only `revision` and JSON `data`. It ignored both `createdAt/updatedAt` and its four persisted secondary index fields, despite the API contract's “identical ⇒ skipped; different ⇒ CONFLICT_REVISION” and its explicit preservation of restored timestamps. A duplicate restore carrying changed timestamps or indexes therefore silently passed while leaving an observably different persisted row untouched.

The bounded correction compares the entire stored row's stable restored fields, including both timestamps and all four index tuple entries, before reporting `identical`. Conflicting duplicate metadata now returns the existing `CONFLICT_REVISION` error. The absent-row restore path, positive-safe-revision admission, unchanged exact duplicates and normal CAS paths are untouched. Index differences are surfaced instead of silently reported as recovered. Existing signed bytes and identity remain unchanged.

The shared cross-adapter regression creates a revision-2 archived record; three attempts with changed creation time, update time or secondary index must conflict while the original record and indexed query remain unchanged. An actual equal repeat must return `identical`. The contract suite is invoked for memory, SQLite and fake IndexedDB, subject to execution.
