# Commerce milestone: exact money precision

Base: PR #41 `560b328dd335aebdc12de01ec339c43ebd164be3`, local shared branch
`codex/parallel-completion-20261116`. No remote changes or commits by this team.

## Completed implementation

F09.S03.M03 now has a real pure TypeScript library at
`packages/commerce/src/valuation/precision/index.ts`. Its exports cover the
specified constructor/parser/formatter, add/subtract/negate/sign/compare/sum,
exact rational conversion, basis-point percentages, fee caps, largest-remainder
allocation and even split. `Money` is immutable bigint in memory, with explicit
`toWire` serialization. Inputs and results enforce 38-digit amount bounds,
40-digit positive rational components, 0–18 decimal exponents and bounded
collections. Unknown numeric fractions, invalid currency syntax and invalid
rounding requests fail with stable typed errors; mixed currencies throw without
including values. Conversion performs one HALF_EVEN rounding at the end.

Added package exports for `@classrup/commerce` and
`@classrup/commerce/valuation/precision`. With root approval, added
`packages/kernel/src/errors/index.ts` and the `@classrup/kernel/errors` export
which reexports existing error/result helpers without pulling in runtime schemas.
No canonical error implementation was copied. The initial kernel barrel import
made the bundle exceed the module's size budget; the narrow import fixes that.

A fresh independent review (`fresh_money_review`) checked malformed values,
rounding, negative allocations, boundaries and bundle size. Its concrete size
finding was fixed. It found no additional correctness blocker in the reviewed
arithmetic. `sign()` was added because SPEC responsibilities require it although
the separate API note omitted it; negative, zero, positive and malformed inputs
are tested. The library has no storage, clock, network, logs or signed statements.

## Remaining commerce blockers

Purchase offers depend on seller terms, quantity/variant inventory, authenticated
acceptance, atomic holds and Deal creation. Payment claims require agreed
obligations and context binding; receipts require those authenticated claims.
Current Mutiny `ProposalSnapshot.legs[].valueMinor` is the declared value of an
item, **not an agreed cash obligation**. Therefore no payment claim resolver was
fabricated from committed barter coordination. No payment-custody, settlement,
canonical offers/receipts, or full commerce completion is claimed.
