# Client-owned messaging, payment evidence and peer transport
Status: **SPECIFIED_REVIEW_PENDING**. MPF-001..004 retained with explicitly revised local semantics. Owners F08 messaging, F09 payment evidence, F11 peers, F10 privacy, F16 cryptographic profile. Inherits [core](CORE_API_EVENTS_DATA.md). No product data backend or secret custody.

## Messaging is fail-closed (MPF-001)
Local message drafts are permitted in memory only, explicitly unsent and cleared on close, with no event/outbox/adapter traffic; durable drafts require reviewed protected storage. In-app message send/receive/import/attachment relay is **disabled** until an independently reviewed encryption protocol specifies authentication, key discovery/verification, recipient/device membership, forward secrecy/recovery tradeoffs, rotation/revocation, backup protection, replay/order handling, metadata leakage, abuse evidence and interoperable test vectors. No plaintext fallback, TLS-only confidential relay, homemade encryption, or E2EE claim. API `message.send(...)` returns PROTOCOL_NOT_REVIEWED with no durable body, event or outbox item; `message.receive(...)` rejects likewise. No product relay can read message plaintext. Users may arrange contact outside the application with explicit disclosure of the selected external service's limits.
Reserved post-review model: Thread `{id,subject_ref,participant_key_refs,state,revision}`; Message `{id,thread_id,sender_key_ref,client_message_id,protocol_version,key_epoch,encrypted_envelope,causal_refs,created_at}`. This is a shape constraint, not an approved wire format. Maximum envelope 64KiB and separately reviewed attachment <=10MiB, local dedup `(thread_id,sender_key_ref,client_message_id)`; same ID/different bytes quarantined. No server sequence/global order/delivery guarantee. Future UI must show sender-local order, gaps/concurrency and provenance, local commit separately from transport ACK/recipient receipt. Removed local membership prevents new local access, cannot retract keys/plaintext already held by recipients. Ciphertext persistence and encryption-at-rest claims await key/storage review as well.

## Settlement evidence, no custody (MPF-002)
`PaymentClaim {claim_id,proposal_ref:{id,revision,digest},claimant_principal_id,payer_principal_id,payee_principal_id,rail:cash|bank_direct|crypto_external|card_external,currency,amount_minor,reference_fingerprint,status:claimed|withdrawn|disputed,created_at}`. `Evidence {evidence_id,claim_id,source_kind:counterparty_assertion|user_selected_provider|user_selected_chain_observer,source_id,status:unverified|observed|source_confirmed|revoked|failed,observed_at,proof_ref,confirmations?,network?,external_id?,policy_version}`. Reference fingerprints/proofs remain private local evidence; public exports exclude them.
`payment.recordClaim`, `payment.recordOwnAcknowledgment`, `payment.importEvidence` are local commands with CR-002 receipts. Only involved unlocked principal records own assertions. Unknown proposal/changed digest returns PROPOSAL_CHANGED; amount/currency mismatch VALIDATION_FAILED; source unavailable retains pending/unverified with DEPENDENCY_UNAVAILABLE adapter error, never synthesizes verification. No payment gateway/webhook/API is mandatory product infrastructure. Optional provider evidence must be fetched/verified by user-selected capable verifier or imported with provenance. Browser clients may lack webhook endpoints, CORS access or safe secret storage; disable that adapter rather than embed provider secrets or require product server. Reviewed adapter must specify signature/source authentication, audience, event dedup, proposal binding, expiry and revocation before enablement. A verifier's signed assertion is only that source's evidence.
Browser redirects/screenshots/buyer statements/unsigned webhooks cannot set source_confirmed. Cash/payee acknowledgment is bilateral assertion, never independent confirmation. Chain-specific confirmation/reorg policy is a blocker for chain adapter; revoke evidence on reorg and flag any prior handover disputed. Labels: claimed, counterparty acknowledged, observed by [source], source-confirmed under [policy], revoked/unknown. No generic settled/final label or automatic asset release. No product-held keys/PAN/bank credentials, custody or refund guarantee.

## Optional peer import/export (MPF-003)
Default OFF, selected destinations require explicit user consent per projection. Peers/storage are replaceable untrusted transports; local draft/edit/search do not require them. Reviewed future record shape `{version,record_id,origin_principal_id,origin_object_id,owner_key_ref,kind:listing_public|tombstone|profile_public,revision,created_at,expires_at?,visibility:public,payload,prev_digest?,profile_id,signature}`. Versioned crypto profile must settle canonicalization, digest/signature algorithms/domain separation/key trust and test vectors; prior fixed Ed25519/JCS text is superseded, not approval to implement. Until review, import/export return PROTOCOL_NOT_REVIEWED without transmission/indexing.
Post-review pipeline: bound <=64KiB envelope and <=100 records/batch -> schema/unknown-field/type check -> signature/key trust verification -> expiry/clock uncertainty/local policy -> dedup/conflict/tombstone checks -> quarantined local projection -> explicit local review -> indexing. Invalid signature/private field rejects; unknown/revoked locally known key, unsupported schema/version or missing predecessor quarantines without indexing; oversized batches/floods throttle per selected peer before parse and never starve local commands. Signatures prove key authorship only, not truthful listing, human identity, legal goods or inventory exclusivity. Do not fetch arbitrary embedded URLs, execute HTML or expose local network addresses through media imports.
Index origin by `(origin_principal_id,kind,origin_object_id)` rather than relay identity; identical object via different relays deduplicates. Same revision/different valid signed digest quarantines entire origin object and stops action/indexing. Preserve both evidence refs; no arrival/time/digest winner, and later revision alone cannot clear fork. Older replay cannot override known tombstone; higher revision resurrection requires explicit owner-authorized new lifecycle and local review under future profile. A tombstone only requests local hiding; cannot erase remote copies. Key revocations can be unseen offline and cannot retrospectively erase data/signatures. Lost-key recovery/rotation and restoration must avoid silently trusting a new key as old owner.
Outbox statuses `queued|attempting|peer_acknowledged|retry_wait|dead_letter|cancelled_local`; local queue durable independent of destination. Retry while app running: full jitter exponential 1s to 6h, max20 attempts then user-visible dead-letter, manual retry same record ID. No browser-closed execution guarantee. ACK stores selected peer ID/evidence/time only, never indexing/global delivery/consent. Inbox transaction and projection dedup use CR-004. Reconnection/snapshot imports honor retained tombstones/conflicts; restore defaults outbound queue paused pending review. User deletion of anti-replay history must warn about possible resurrection. Peer ordering/time and snapshot completeness are untrusted.
